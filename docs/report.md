# DSH Live ETA — 本轮验证与改进报告

日期：2026-11-08
环境：DSH Desktop 0.2.2-rc.1（Windows），Profile `desktop`，模型 `bailian/deepseek-v4.1-flash-1017`。
数据：本机 46 个真实会话、39 个完成的 turn，其中 16 个运行时长 ≥60 秒，共 336 个预测采样点。

## 1. 结论：一个区间到底有多大概率可信

现在面板直接给出经验概率，例如：

> 剩余 1.4–30.6 分钟 · **区间把握 约 69%（n=149）**

这个数字不是模型自评，而是：取历史上同一进度桶（早/中/晚）的“实际剩余 ÷ 预测中位数”比值，统计落入当前区间相对位置的比例，再做拉普拉斯平滑。样本不足 8 个预测点时显示“样本不足，暂不给出概率”。

用 17 个真实任务做留出式回放（learned 模式下先验和分桶模型只用更早任务）后，区间在三个检查点的实际覆盖率：

| 检查点 | 覆盖率 | 绝对误差中位数 |
| --- | --- | --- |
| 进度 25% | 82% | 6.1 分钟 |
| 进度 50% | 77% | 5.9 分钟 |
| 进度 75% | 69% | 9.2 分钟 |

上一版（未加工作区/时间衰减/计划先验）同口径为 70% / 75% / 67%，误差 6.8 / 5.3 / 6.1 分钟。样本只有 17 个任务，75% 处误差反而变大，属于抽样波动，不能据此认为模型退化。

也就是说：界面显示“区间把握约 70%”时，历史回放里确实约有 2/3–4/5 的情况落在该区间。样本只有 17 个任务，置信区间很宽，这个结论只对本机已有的任务类型成立。

## 2. 改进前后对比（同一批真实任务）

| 指标 | cold（纯静态先验） | learned（历史校准） |
| --- | --- | --- |
| 25% 进度覆盖率 | 54.5% | **81.8%** |
| 50% 进度覆盖率 | 41.7% | **76.9%** |
| 75% 进度覆盖率 | 13.3% | **68.8%** |
| 25% 进度 MAE | 8.5 分钟 | **6.1 分钟** |
| 50% 进度 MAE | 10.8 分钟 | **5.9 分钟** |
| 75% 进度 MAE | 13.4 分钟 | 9.2 分钟 |
| 初始预测 MAE | 13.6 分钟 | **13.3 分钟** |
| 大幅跳变次数/任务 | 0.29 | 0.88 |

要点：

- 中期和后期误差下降约 30–45%，覆盖率翻倍到接近名义的 70%，**不是靠把区间无限拉宽**（区间来自分位，宽度受 15%/85% 约束）。
- 初始预测没有变好，反而略差：静态类别先验对“本机真实任务”反而更接近， pooled 历史会向短任务偏移。因此初始值只作为参考，真正起作用的是执行中的校正。
- 大幅跳变从 0.25 升到 0.88 次/任务：分桶校正生效时会一次性调整，属于“有依据的修正”，但仍偏多，后续会用滑动窗口降低抖动。

## 3. 模型改动

1. **待办不再等同于时间进度**：待办按措辞赋权（测试/验证 1.5、修复 1.2、文档 0.8），剩余时间 = 加权剩余工作量 × 实测单位速度；完成条数只用于展示。
2. **阶段份额来自历史**：每个阶段的期望耗时用同类任务的阶段耗时中位数；未开始的阶段按份额计入。
3. **无待办时用生存模型**：对数正态先验下“已运行 E 后的剩余中位数”，与“先验剩余”加权，避免早期过度乐观或后期不收敛。
4. **分桶偏差校正**：按进度早/中/晚三桶，用历史“实际剩余/预测中位数”的中位数做乘性校正；同桶的 15%/85% 分位作为区间。
5. **概率**：同一桶的经验分布 + 平滑，样本不足返回 null。
6. **追加需求、重复失败、长工具**：保留原有修正，但都改为随时间衰减（错误 3 分钟、重复 6 分钟、追加 20 分钟），避免一次异常把 ETA 顶死。
7. **工作区分桶**：先验按 `cwd → 模型 → 类别` 逐级收窄，同一项目完成 ≥3 个任务后优先用项目分布，解决不同项目量级差 5 倍的问题。
8. **时间衰减**：历史记录按 30 天半衰期加权，近期任务主导中位数，能跟上工作方式变化。
9. **计划先验**：第一次出现待办时，用历史“每单位计划耗时”的中位数初始化速度，估计立刻与计划规模匹配，而不是等完成两三条待办才校准。

## 4. 真实任务与回放

- 回测接口 `POST {"action":"backtest"}` 只读打开历史会话，逐个重放完成的 turn；同一批 turn 跑两遍（cold / learned），结果按 `会话#turn` 去重写入本地历史，因此回测一次后线上概率立即可用。
- 实测：46 个会话、39 个 turn、16 个可评估任务（≥60 秒）、336 个预测点，耗时 2.3 秒；单次请求预算 20 秒，不会阻塞 UI。
- 线上本次开发任务（约 55 分钟）也在跟踪：待办 4/5、当前阶段“修改与实现”、区间与概率随进展变化。该任务已超过历史最长任务（21 分钟），属于分布外，区间偏窄、概率偏低，已在局限中注明。

## 5. 首次预测与 UI

- 空闲轮询从 20 秒降到 1.5 秒，运行中 5 秒、结束后 15 秒；任务开始后最迟 1.5 秒出现区间，且不增加任务启动延迟（轮询在宿主侧只读内存状态）。
- 面板新增“区间把握”、25/50/75% 覆盖、上次有效进展（时间 + 距今多久 + 动作）。
- 胶囊仍在输入框工具行（`conversation.input.left`），浮层 portal 到 body，未改变布局；停用后不渲染任何东西。
- 面板新增“计划”区，展示待办列表与状态；胶囊显示完成数（如 `· 3/5`）。
- 内置待办面板（`conversation-todo-dock`）属于 `@deepseek-ai/dsh-client-ui-conversation`，不是独立插件，无法用 `plugin_manager` 单独禁用——禁用 `ui-conversation` 会连聊天界面一起消失。曾尝试用同 id `todo` 接管该 slot，实测被内置注册优先占用，未生效；因此保留内置面板，改为在数据与扩展面板层面合并。

## 6. 兼容性与安全

- 事件读取顺序改为：`Session.snapshotEvents()` → `ownEvents()` → `sessionQuery.readSession()`。`ownEvents()` 在当前版本仍可用，但不再承担主路径；即使未来移除，另两条路径仍能工作。冷会话用 `readSession()`（官方“live or persisted”读取）。
- 恢复耗时从约 1.5 秒降到约 30 毫秒（优先读内存事件，避免重放校验整个持久化日志）。
- HTTP 端点增加 loopback 校验（127.0.0.1 / ::1），非本机来源返回 403；响应只含短标签与计数，不含消息正文或工具参数。
- 仍为零 LLM 调用、零上下文注入、零工具注册；所有事件处理 try/catch，失败只累加内部计数。

## 7. 性能

| 指标 | 实测 |
| --- | --- |
| 事件处理 | 3.2–7.6 µs/事件 |
| 状态接口（服务端） | 0.43 ms/次，2.4 KB |
| 重载后恢复 | ~30 ms |
| 回测 | 46 会话 ~2.3 s（按需） |
| 轮询 | 1.5 s / 5 s / 15 s |

## 8. 局限

1. 样本只有 16 个 ≥60 秒的真实任务，覆盖率 70/75/67% 的抽样误差约 ±12%，不足以证明长期稳定。
2. 分类仍是关键词规则；长任务、跨领域任务的先验偏差只能靠执行中的校正。
3. 超过历史最长任务时长（当前 21 分钟）后，分布外推断偏乐观；需要更多长任务样本。
4. 初始预测没有改善（MAE 14.2 分钟），仅作参考；真正的价值在 25% 进度之后。
5. 大幅修正次数偏多（0.88 次/任务），下一步会加滑动窗口和最小停留时间。
6. UI 只做了 slot 注册与代码级检查，未做像素级截图比对（当前模型不能读图）。

下一步优先级：更多长任务样本 → 降低分桶切换抖动 → 用阶段/工具序列做二次分类 → 可选的侧边栏历史面板。
